# BizOrder Assistant 프로젝트 기획서 v1.0

> 2026-10 재정의: 특정 회사용 내부 업무 시스템이 아니라 **정책 기반 견적 계산 문제를 보여주는 포트폴리오 웹 시스템**을 중심으로 범위를 재구성한다.

## 1. 프로젝트 목적

가격·약정·할인 조건이 복잡하고 자주 바뀌는 B2B 상품 환경에서, 특정 시점의 견적을 일관되게 계산하고 그 이유를 설명할 수 있는 시스템을 만든다.

포트폴리오에서 보여주고 싶은 것은 단순 CRUD 수가 아니라 다음 능력이다.

- 업무 규칙을 도메인으로 모델링하는 능력
- 시점과 조건에 따라 유효한 정책 하나를 결정하는 로직
- 가격과 할인 규칙을 코드가 아닌 데이터로 관리하는 설계
- 할인 충돌과 우선순위를 처리하는 결정론적 계산
- 정책 변경과 과거 확정 견적을 분리하는 Snapshot 설계
- PostgreSQL / REST API / 테스트 / Frontend까지 이어지는 완성된 서비스 흐름

## 2. 프로젝트 성격

BizOrder Assistant는 특정 통신사나 특정 회사의 실제 업무 시스템을 복제하지 않는다.

통신형 B2B 상품은 **가격정책과 약정조건을 설명하기 좋은 예시 도메인**으로 사용한다. 실제 고객 개인정보, 실제 사내 상품 코드, 비공개 요금정책, 공식 시스템 API는 사용하지 않는다.

따라서 프로젝트의 질문은 “어느 회사가 실제로 이 프로그램을 쓰는가?”가 아니라 다음이다.

> **복수의 가격·할인 정책이 존재할 때, 주어진 조건에서 어떤 정책을 적용해야 하며 왜 그런 결과가 나왔는가?**

## 3. 핵심 사용자 경험

### 견적 작성자
상품, 수량, 약정기간, 견적 기준일과 필요한 조건을 입력한다.

시스템은 다음을 반환한다.

- 선택된 가격 정책
- 적용된 할인
- 적용되지 않은 할인과 이유
- 기본 금액 / 할인 금액 / 최종 금액
- 계산 근거

### 정책 관리자
Product / PricingPolicy / DiscountRule을 가상 데이터로 관리한다.

정책 변경은 새 견적에는 반영되지만 이미 확정된 견적의 Snapshot에는 영향을 주지 않는다.

## 4. 핵심 시나리오

```text
ADMIN
  └─ Product 등록
  └─ 약정기간·유효기간별 PricingPolicy 등록
  └─ DiscountRule 등록
                ↓
STAFF
  └─ 상품 / 수량 / 약정 / 견적일 / 조건 입력
                ↓
        유효 PricingPolicy 선택
                ↓
          DiscountRule 평가
                ↓
       할인 충돌·우선순위 해결
                ↓
        최종 견적 + 계산 근거
                ↓
             확정
                ↓
        Quote Snapshot 보존
```

## 5. MVP 도메인

### Product
견적 가능한 가상 상품. 식별코드, 이름, 카테고리, 활성상태를 가진다.

### PricingPolicy
특정 Product에 적용되는 가격 정책. 최소한 약정기간, 월 이용료, 유효 시작/종료 시점을 표현한다.

### QuoteRequest
견적 계산 입력. 상품, 수량, 약정기간, 견적 기준일과 할인 판별에 필요한 비식별 조건을 가진다.

### Quote / QuoteItem
견적 계산 결과. 선택된 정책, 수량, 기본금액, 할인 결과, 최종금액을 표현한다.

### DiscountRule
정액/정률 할인, 적용 조건, 유효기간, 우선순위, 중복 가능 여부를 데이터로 표현한다.

### AppliedDiscount
실제 견적 계산 과정에서 적용된 할인 결과.

### Snapshot
견적 확정 당시 상품·가격정책·할인·금액을 복사해 보존한 데이터.

## 6. MVP에서 가장 중요한 비즈니스 규칙

1. 비활성 Product는 새 견적에 사용할 수 없다.
2. 견적 기준일과 약정기간에 맞는 PricingPolicy만 후보가 된다.
3. 동일 조건에서 어떤 PricingPolicy를 선택할지 모호하면 안 된다.
4. 가격정책이 존재하지 않으면 조용히 0원 처리하지 않고 명시적으로 실패한다.
5. DiscountRule은 조건을 만족할 때만 적용한다.
6. 만료된 할인은 적용하지 않는다.
7. 중복 불가 할인끼리 충돌하면 명시된 우선순위로 해결한다.
8. 할인 결과가 비정상적인 음수 금액을 만들지 않는다.
9. 계산 결과에는 “무엇이 적용되었고 무엇이 제외되었는지” 설명 가능한 정보가 남는다.
10. 확정된 Quote는 이후 정책 변경으로 다시 계산되지 않는다.

## 7. 개발 순서 원칙

초기 계획처럼 Backend를 끝까지 만든 뒤 Frontend를 붙이지 않는다.

```text
Product
  ↓
PricingPolicy
  ↓
유효 가격 선택
  ↓
Quote Engine v1
  ↓
★ 최소 Frontend 연결
  ↓
Discount Engine
  ↓
Snapshot
  ↓
Auth / CI / Demo 마무리
```

Quote Engine v1이 나오면 최소한의 React 화면을 바로 연결한다. 이후 정책 기능을 추가할 때마다 실제 화면에서 계산 결과가 변하는 것을 확인한다.

## 8. MVP 범위에서 내린 것

다음 기능은 프로젝트 정체성을 설명하는 데 필수가 아니므로 핵심 MVP에서 제외하거나 후순위로 둔다.

- 가입 접수 Checklist
- 고객 CRM
- 상담 이력 관리
- 실제 BSS/SWING 연동
- 실제 개인정보
- AI 추천
- 통계 대시보드
- 알림
- PDF 견적서
- 복수 사업장
- 실제 결제/정산

Checklist는 핵심 엔진과 데모가 완성된 뒤 여유가 있을 때 Stretch 기능으로 다시 검토한다.

## 9. Frontend 최소 목표

초기 화면은 디자인 완성도가 아니라 엔진을 눈으로 확인하는 것이 목적이다.

최소 화면:

1. Product / PricingPolicy 관리
2. 견적 입력
3. 견적 결과
4. 계산 근거
5. 확정 견적 조회

예시:

```text
상품        Biz Internet 500M
약정        36개월
수량        2
견적일      2026-10-02

[견적 계산]

적용 정책    2026 하반기 36개월 정책
기본 금액    64,000원
할인         -8,200원
최종 금액    55,800원

[계산 근거 보기]
```

## 10. 핵심 테스트 전략

테스트 개수를 늘리는 것이 목적이 아니라 **업무 규칙의 경계**를 검증한다.

우선순위:

- 날짜 경계: validFrom / validTo 당일
- 약정기간 일치/불일치
- 같은 조건의 정책 중복/모호성
- 비활성 Product
- 가격정책 미존재
- 할인 조건 충족/불충족
- 할인 유효기간
- 중복 불가 할인 충돌
- 우선순위 동률/결정 규칙
- 정률/정액 할인 계산
- 0원 이하 방지
- 확정 후 정책 변경에도 Snapshot 불변

실제 PostgreSQL과 HTTP 통합 테스트는 핵심 시나리오 위주로 유지하고, 순수 계산 규칙은 가능한 한 단위 테스트로 빠르게 검증한다.

## 11. 기술 스택

Backend: Java 21, Spring Boot 4.1.1, Spring Web MVC, Spring Data JPA, Spring Security, Validation, Flyway, JUnit 5  
Database: PostgreSQL 18  
Frontend: React, TypeScript  
Infrastructure: Docker, Docker Compose, GitHub Actions  
Documentation: OpenAPI/Swagger, ERD, Architecture

## 12. 성공 기준

완성된 저장소와 데모만 보고 다음 질문에 답할 수 있어야 한다.

- 왜 Product와 PricingPolicy를 분리했는가?
- 특정 날짜와 약정조건에서 가격정책을 어떻게 선택하는가?
- 정책이 겹치면 어떻게 모호성을 제거하는가?
- 할인 충돌은 어떤 규칙으로 해결하는가?
- 최종 가격이 나온 이유를 어떻게 설명하는가?
- 정책을 수정했는데 왜 과거 확정 견적은 바뀌지 않는가?
- 어떤 규칙을 단위 테스트하고 어떤 흐름을 통합 테스트했는가?

## 13. 포트폴리오 설명 문장

> 가격·약정·할인 조건이 변하는 B2B 상품을 대상으로, 가격과 할인 정책을 코드에서 분리해 데이터로 관리하고 특정 시점의 유효 정책을 결정론적으로 선택하는 견적 엔진을 구현했습니다. 할인 충돌과 우선순위를 처리하고 계산 근거를 반환하며, 확정 견적은 Snapshot으로 보존해 이후 정책 변경에도 과거 결과를 재현할 수 있도록 설계했습니다.
